# ADR-001 - Redis para o estado das conversas do chatbot

**Data:** 04/11/2026. **Responsável documental:** Core4 Tech. **Estado:** Consolidação de decisão registrada pela equipe na Aula 3; parâmetros e fallback propostos na E2.

## Contexto

A Aula 3 já escolheu Redis para sessões frequentes do bot. Preservamos ADR-001 e seu propósito. A alegação de gargalo no banco relacional é motivação/hipótese da equipe, não benchmark comprovado.

## Decisão

Manter Redis para estado transitório; TTL proposto de 30 min para conversa e 30 s para cache de slots. Cache nunca reserva horário. Confirmação depende de commit no PostgreSQL e identidade vinculada. Estado mínimo sem conteúdo clínico. Falha de Redis reinicia conversa e oferece recepção, mantendo web operacional.

## Alternativas consideradas

PostgreSQL para sessão: reutiliza operação e é durável, mas aumenta escritas e limpeza de registros temporários. Memória da JVM: custo baixo, porém perde estado ao reiniciar e dificulta múltiplas instâncias. Redis adiciona serviço, mas centraliza expiração e sessões.

## Trade-offs e custo/benefício

Benefício: operações rápidas e TTL nativo, menor carga transitória no banco principal. Custo de implementação médio (adaptador e fallback), operação média contínua (memória, rede, monitoramento). Aceita-se perda de conversa; não se aceita usar cache como verdade de agenda. Não há orçamento financeiro/cotação nas fontes.

Custos são avaliações qualitativas relativas, não estimativas financeiras aprovadas.

## Verificação e revisão

Injetar falha do Redis, expirar sessão e apresentar slot obsoleto; exigir web operante e recusa transacional do slot ocupado. Reavaliar se volume não justificar manutenção do serviço.
